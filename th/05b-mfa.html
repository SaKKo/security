05b · การยืนยันตัวตนหลายปัจจัย (MFA)

ปัจจัยที่สองทำให้รหัสผ่านที่ถูกขโมยไปไม่พอสำหรับการเข้าระบบอีกต่อไป แต่จะได้ผลก็ต่อเมื่อปัจจัยนั้นแยกจากรหัสผ่านจริง เดาไม่ได้ และทุกเส้นทาง login ตรวจมันเสมอ

Rails ไม่มี MFA ในตัว คุณต้องเลือกส่วนประกอบเอง: rotp สำหรับ TOTP, encrypts สำหรับเก็บ secret, Rack::Attack สำหรับจำกัดจำนวนครั้ง และ webauthn สำหรับ passkey
ใช้แอป authenticator (TOTP) หรือ passkey เก็บ TOTP secret แบบเข้ารหัส ตรวจที่ server ด้วยช่วงเวลาคลาดเคลื่อนเล็กๆ ปฏิเสธรหัสที่ใช้ไปแล้ว จำกัดจำนวนครั้งที่ลอง ยืนยันการลงทะเบียนด้วยรหัสแรก และบังคับตรวจในที่เดียวที่ทุกเส้นทาง login ต้องผ่าน อย่าคิดระบบ "รหัสสุ่ม" ขึ้นมาเอง

อะไรนับเป็นปัจจัยที่สอง

ปัจจัยคือสิ่งที่คุณรู้ (รหัสผ่าน) สิ่งที่คุณมี (โทรศัพท์, security key) หรือสิ่งที่คุณเป็น (ลายนิ้วมือ) รหัสผ่านสองตัวก็ยังเป็นปัจจัยเดียว เป้าหมายคือ ผู้โจมตีที่ได้รหัสผ่านของคุณจากการ phishing หรือซื้อมา ก็ยัง login ไม่ได้

วิธีความแข็งแรงจุดอ่อน
Passkey / security key (WebAuthn)ดีที่สุดผูกกับโดเมนจริง เว็บ phishing จึงไม่ได้อะไรเลย
แอป authenticator (TOTP)ดีหน้า phishing ที่ทำงานแบบ real-time ส่งต่อตัวเลข 6 หลักได้ภายใน 30 วินาที
การกดอนุมัติแบบ pushพอใช้"MFA fatigue": ส่งคำขอรัวๆ จนมีคนกดยอมรับ
รหัสทาง SMS / emailอ่อนSIM swap, การดักจับ SS7 หรือบัญชีอีเมลเป็นบัญชีเดียวกับที่ถูกโจมตี

ทำไมไม่เก็บตัวเลขสุ่มแล้วเทียบใน controller ไปเลย?

มันดูเหมือน MFA และเป็นแบบทำเองที่เราเจอบ่อยที่สุดตอนรีวิวโค้ด:

# ✗ home-made "2FA"
class Api::V1::SessionsController < Api::V1::AppController
  def create
    user = User.find_by!(username: params[:username])
    raise AppAuthenticationError unless user.authenticate(params[:password])
    code = rand(100000..999999).to_s
    user.update!(otp_code: code)                      # plaintext, no expiry
    update_cookies(:bearer, user.jwt("bearer"))       # session issued already!
    render json: { success: true, otp: code }         # "the app shows it to the user"
  end

  def verify_otp
    if params[:code] == current_user.otp_code         # unlimited tries, reusable
      current_user.update!(otp_verified: true)        # one flag for all sessions
      render json: { success: true }
    else
      render json: { success: false }, status: :unauthorized
    end
  end
end

ลองนับปัญหาดู แล้วแก้ทีละข้อใน lab ด้านล่าง และดูว่าการโจมตีไหนยังได้ผลอยู่:

lab: โจมตี 2FA แบบทำเองเปิดปิดการแก้ไขแล้วดูผล

แม้ติ๊กครบทุกข้อ แบบทำเองก็ยังเป็นแค่ SMS code เวอร์ชันที่อ่อนกว่า: คุณต้องดูแลการส่ง การหมดอายุ การ hash การล็อก และจุดตรวจ session เอง TOTP ตัดการเก็บรหัสออกไปทั้งหมด bug ทั้งกลุ่มจึงหายไป

"ใน controller" คือส่วนหนึ่งของ bug เรามีเส้นทาง login สองทาง (Admin::SessionsController#create และ Client::AuthController#login) การตรวจที่ copy ไปวางใน controller หนึ่ง คือการตรวจที่หายไปจากอีก controller หนึ่ง ให้เก็บการตรวจไว้ใน model (user.verify_otp) และให้ทุกเส้นทาง login เรียกมันก่อนออก session หรือ token ใดๆ

brute force ขึ้นกับจำนวนครั้งที่ลอง ไม่ใช่จำนวนหลัก

ตัวเลข 6 หลักมีความเป็นไปได้แค่หนึ่งล้านแบบ สิ่งที่ปกป้องมันคือจำนวนครั้งที่คุณยอมให้เดา ลองปรับตัวเลขดู:

เครื่องคิด: โอกาสที่ผู้โจมตีเดารหัสถูกปรับค่าจำกัด

ไม่จำกัดครั้งที่ 10 ครั้ง/วินาทีเป็นเวลาหนึ่งวัน: แทบแน่นอนว่าสำเร็จ ห้าครั้งต่อ 15 นาทีเป็นเวลาหนึ่งเดือน: ประมาณ 1.4% ล็อกบัญชีหลังรหัสผิด 10 ครั้งและแจ้งผู้ใช้: 0.001% ให้จำกัดทั้งต่อบัญชีและต่อ IP และนับ OTP ที่ผิดแยกจากรหัสผ่านที่ผิด

TOTP ทำงานอย่างไร

  1. ตอนลงทะเบียน server สร้างsecret แบบสุ่มแล้วแสดงครั้งเดียว ในรูป QR code ของ URI otpauth:// โทรศัพท์จะเก็บค่านี้ไว้
  2. ทั้งสองฝั่งคำนวณ T = floor(unix_time / 30)
  3. ทั้งสองฝั่งคำนวณ HMAC-SHA1(secret, T) แล้วตัดเหลือ 6 หลัก (RFC 6238)
  4. หลังลงทะเบียนแล้ว server ไม่ส่งอะไรไปที่โทรศัพท์อีกเลย secret เดียวกัน + นาฬิกาเดียวกัน = รหัสเดียวกัน
ของจริง: TOTP ที่คำนวณในเบราว์เซอร์ของคุณพิมพ์รหัสจากโทรศัพท์ใส่ฝั่ง server

ลองดู: กด ใช้รหัสจากโทรศัพท์ สองครั้ง ครั้งที่สองจะถูกปฏิเสธเมื่อเปิดการกันใช้ซ้ำ และถูกยอมรับเมื่อปิด เลื่อนนาฬิกาโทรศัพท์ไปที่ −30 วินาที: drift_behind: 1 ยังยอมรับ แต่ −60 วินาทีจะไม่ผ่าน คุณยังพิมพ์ secret ลงในแอป authenticator จริงแล้วดูว่ามันแสดงรหัสเดียวกันได้ด้วย

สอง flow หลัก

ในโค้ด Rails ของเรา

class User < ApplicationRecord
  encrypts :otp_secret                       # Active Record encryption at rest
  # ApplicationRecord: has_paper_trail skip: [:otp_secret], as_json drops "otp" columns

  def enable_two_factor!
    raise AppError.new("Two-factor authentication is already enabled. Disable it first.") if otp_required?
    self.otp_secret = ROTP::Base32.random
    self.otp_required = false                # not on until confirmed
    save!
  end

  def confirm_two_factor!(code)
    verify_otp(code) ? update!(otp_required: true) : false
  end

  def verify_otp(code)
    return false if otp_secret.blank? || code.blank?
    !totp.verify(code.to_s.strip, drift_behind: 1).nil?
  end

  def provisioning_uri
    totp.provisioning_uri(email.presence || username) if otp_secret.present?
  end

  def totp
    @totp ||= ROTP::TOTP.new(otp_secret, issuer: "MyApp")
  end
end

ส่วนที่ดีอยู่แล้ว: secret ถูกเข้ารหัส และไม่อยู่ใน audit log และ JSON การลงทะเบียนยืนยันด้วยรหัสแรก การตรวจอยู่ใน model และทั้งสองเส้นทาง login ปฏิเสธผู้ใช้ที่ไม่มี otp_required? และตรวจรหัสก่อนออก cookie หรือ token สิ่งที่ควรเพิ่ม:

1. ปฏิเสธรหัสที่ใช้ไปแล้ว

# migration: add_column :users, :otp_last_used_at, :bigint

def verify_otp(code)
  return false if otp_secret.blank? || code.blank?
  ts = totp.verify(code.to_s.strip, drift_behind: 1, after: otp_last_used_at)  # nil if reused
  return false unless ts
  update_columns(otp_last_used_at: ts)
  true
end

2. จำกัดจำนวนครั้งในการตรวจ OTP

# config/initializers/rack_attack.rb
Rack::Attack.throttle("logins/username", limit: 5, period: 5.minutes) do |req|
  if req.post? && ["/api/v1/admin/sessions", "/api/v1/client/auth/login"].include?(req.path)
    (req.params.dig("user", "username") || req.params["username"]).to_s.downcase.presence
  end
end

3. recovery code ที่ hash แล้วและใช้ได้ครั้งเดียว

def generate_recovery_codes!
  codes = Array.new(10) { SecureRandom.alphanumeric(10).downcase }
  update!(otp_recovery_digests: codes.map { BCrypt::Password.create(_1) })   # store hashes only
  codes                                                                       # show once
end

def use_recovery_code!(code)
  digest = otp_recovery_digests.find { BCrypt::Password.new(_1) == code.to_s.strip.downcase }
  digest ? update!(otp_recovery_digests: otp_recovery_digests - [digest]) : false
end

4. ปกป้องปุ่มปิด

disable_two_factor! ควรต้องใส่รหัสผ่านใหม่และรหัส OTP ปัจจุบัน บันทึก audit event และแจ้งผู้ใช้ทางอีเมล ผู้โจมตีที่ขโมย session ได้จะพุ่งไปที่ปุ่มนี้ก่อน

เช็กลิสต์

  • ใช้ TOTP หรือ passkey ใช้ SMS เป็นทางสำรองเท่านั้น และห้ามใช้ email อย่างเดียวกับพนักงาน
  • secret: ROTP::Base32.random, encrypts, ไม่อยู่ใน log, JSON และ audit trail และแสดงเฉพาะตอนลงทะเบียน
  • เปิดใช้การลงทะเบียนหลังจากใส่รหัสแรกถูกต้องเท่านั้น
  • การตรวจอยู่ใน model และทุกเส้นทาง login เรียกมันก่อนออก session หรือ token
  • ช่วงคลาดเคลื่อนไม่เกิน 1 step และปฏิเสธ time step ที่ใช้ไปแล้ว
  • จำกัดจำนวนครั้งทั้งต่อบัญชีและต่อ IP และแจ้งเตือนเมื่อผิดซ้ำหลายครั้ง
  • recovery code ที่ hash แล้วและใช้ได้ครั้งเดียว
  • การปิด MFA หรือเปลี่ยนโทรศัพท์ต้องยืนยันตัวตนใหม่และส่งการแจ้งเตือน

endpoint login คืนค่า { otp: "482913" } เพื่อให้แอปมือถือแสดงผล ขั้นที่สองนี้เพิ่มความปลอดภัยเท่าไร?

ปัจจัยที่สองต้องไปถึงผู้ใช้ผ่านช่องทางที่ผู้โจมตีควบคุมไม่ได้

ทำไมการลงทะเบียนต้องขอรหัสแรกก่อนตั้งค่า otp_required: true?

ถ้าไม่ทำ การสแกนที่ล้มเหลวหรือพิมพ์ผิดตอนกรอกเอง จะทำให้บัญชีถูกล็อกในการ login ครั้งถัดไป

ผู้โจมตีเดาได้ 10 ครั้งต่อวินาทีโดยไม่มีการจำกัด TOTP 6 หลักจะถูกเจาะในเวลาประมาณเท่าไร?

การหมุนเวียนรหัสช่วยได้ไม่มาก การเดาแต่ละครั้งมีโอกาสประมาณ 2 ในล้าน และการเดา 864,000 ครั้งต่อวันทำให้สำเร็จได้ค่อนข้างแน่ มีแค่การจำกัดจำนวนครั้งที่แก้ได้
