03 · Unsafe Query Generation

Your query is parameterized and still returns the wrong row. Why? The request parser turned "a string" into null, an array or an object.

The problem: request parsers create types

HTTP sends text, but frameworks helpfully turn it into other types:

requestparsed aswhere
?token=abc"abc"everywhere
?token[]=[""] or [nil]Rails, PHP, Express (qs)
?token[]=a&token[]=b["a","b"]Rails, PHP, Express
?token[$ne]=x{ "$ne": "x" }Express (qs), PHP
{"token": null} (JSON body)nullevery JSON API
{"token": {"$gt": ""}}an objectevery JSON API

Then the query builder does its job: null becomes IS NULL, an array becomes IN (…), and in MongoDB {"$ne": null} matches everyone.

Why it matters

Password reset looks up the user by token. Most users have no token (NULL). Send null and you match a random user, then reset their password. This exact bug hit Rails more than once.

Rails' answer: deep_munge

Rails' deep_munge cleans up shapes like [nil], and params.permit(:token) drops arrays and hashes. But params[:token] used directly can still be anything, and find_by(token: nil) still means IS NULL.

The general fix: validate types at the boundary

Decide the shape of each param and check it first. A token is a non-empty string. Anything else: 400.

  • Use a schema validator (zod, pydantic, or strong params plus type checks in Rails).
  • MongoDB: strip keys starting with $.
  • Never look up by a value that might be empty.
class PasswordsController < ApplicationController
  def update
    token = params[:token]
    return head :bad_request unless token.is_a?(String) && token.present?
    user = User.find_by_password_reset_token!(token)   # Rails 8: signed + expiring
    user.update!(params.permit(:password, :password_confirmation))
    redirect_to new_session_path, notice: "Password updated."
  rescue ActiveSupport::MessageVerifier::InvalidSignature
    redirect_to new_password_path, alert: "Link invalid or expired."
  end
end
